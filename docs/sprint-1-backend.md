# صنعة — سبرنت 1: المواصفة المعتمدة وخطة الباك اند

> **المرجع الوحيد لهذا السبرنت هو التصاميم المعتمدة (13 شاشة).**
> هذه الوثيقة تحل محل قسم سبرنت 1 في وثيقة الـ User Stories القديمة، وما يخالفها فيها يُعتبر ملغى.

**قرارات الفريق المطبّقة هنا:**

1. **تحقق البريد الإلكتروني إلزامي عند التسجيل.** يُنشأ الحساب بـ `email_verified_at = NULL` ولا يُصدر توكن فوراً — يُرسل كود من 6 أرقام، ولا يُصدر التوكن إلا بعد التحقق منه. راجع §5.
2. لا توجد شاشة «حساب قيد المراجعة» — كل الأدوار **المتحقّقة** تدخل فوراً، والتحقق الإداري يجري بالخلفية كشارة ثقة فقط.
3. **شاشة إدخال الكود (12.png) تخدم سيناريوهين الآن**: تأكيد البريد بعد التسجيل، واستعادة كلمة المرور — يُميَّز بينهما بحقل `purpose` (`register` أو `reset`)، وليس بشاشتين منفصلتين.

## 2. مستويات الوصول

- **الزائر غير المسجّل:** يصل فقط إلى المسارات العامة للقراءة — المحافظات، عناوين
  السكن، الخدمات، أنواع النشاط، وعرض الحرفيين. لا ينفّذ أي إجراء (لا تسجيل، لا تعديل، لا حجز).
- **المسجّل غير المتحقق** (`email_verified_at = NULL`): لا يستطيع تسجيل الدخول ولا
  الوصول لأي مسار محمي. عند محاولة الدخول يرد `login` بـ 403 ويُعاد توجيهه لشاشة
  الكود مع كود جديد مُرسل تلقائياً (راجع §5.4).
- **المسجّل المتحقق:** وصول كامل حسب `role` (عميل/حرفي/مؤسسة/مقاول/أدمن)، مع مراعاة
  `status` على `users` (نشط/موقوف) وحالة جدول الدور (`pending`/`approved`/`rejected`
  — لا تمنع الوصول، فقط تتحكم بشارة الثقة).

## 3. المواصفة حسب الشاشات

### S1-01 — اختيار الدور (1.png)

أربع بطاقات: **مؤسسة، مقاول، حرفي، عميل** — كل واحدة بأيقونة ووصف وزر «إنشاء حساب»، وأسفلها «لديك حساب؟ تسجيل دخول».

- الاختيار مجرد توجيه للفرونت — لا يحتاج أي endpoint
- الدور الفعلي يتحدد من نوع endpoint التسجيل المستخدم
- الشاشة تُتخطّى كلياً لمن لديه جلسة صالحة
- **تصحيح مطلوب:** العنوان الفرعي مكتوب «منصة صنعاء» والصحيح «صنعة»

### S1-02 — تسجيل الدخول (2.png)

| الحقل | ملاحظات |
|---|---|
| البريد الإلكتروني | مطلوب |
| كلمة المرور | مطلوب، مع زر إظهار/إخفاء |
| تذكرني | checkbox — يطيل عمر التوكن |
| نسيت كلمة المرور؟ | رابط لـ S1-07 |

**السلوك:**
- **يُفحص `email_verified_at` أولاً** قبل أي شيء آخر — إن كان `NULL` يُرسل كود جديد
  (`purpose=register`) ويرد النظام 403 موجّهاً المستخدم لشاشة الكود، وليس برسالة خطأ عامة
- بعد ذلك: رسالة خطأ **عامة** واحدة لا تكشف أي الحقلين خطأ
- قفل مؤقت 15 دقيقة بعد 5 محاولات فاشلة متتالية
- الاستجابة تحمل `role` ليقرر الفرونت وجهة التحويل
- الحساب الموقوف (`suspended`) لا يستطيع الدخول

**نقص بالتصميم:** لا يوجد رابط «إنشاء حساب» — يُفضّل إضافته للفرونت (لا أثر على الباك اند).

### S1-07 — تحقق البريد واستعادة كلمة المرور (11.png + 12.png + 13.png)

**أ) تحقق البريد بعد التسجيل** (`purpose=register`) — راجع §5.1 للتفصيل الكامل.

**ب) نسيان كلمة المرور** (`purpose=reset`) — ثلاث شاشات بالترتيب:

1. **إدخال البريد** (11.png) → يُرسل كود من 6 أرقام إن كان البريد مسجّلاً، مع رسالة محايدة في الحالتين
2. **إدخال الكود** (12.png) → 6 خانات، البريد مقنّع، عدّاد إعادة إرسال 45 ثانية
3. **كلمة مرور جديدة** (13.png) → كلمة المرور + تأكيدها + قائمة متطلبات تتحدث مباشرة

**القواعد المشتركة بين التسجيل والاستعادة** موحّدة الآن — راجع §5.3.

بعد التحقق من كود `purpose=reset` يُصدر النظام **توكن استعادة قصير الأجل** (وليس توكن دخول)، يُستخدم مرة واحدة مع `reset-password` لتعيين كلمة المرور الجديدة، ثم **تُلغى كل الجلسات والتوكنات السابقة** لصاحب الحساب.

**تصحيح مطلوب:** نص الشاشة الأولى يقول «سنرسل لك رابطاً» والنظام يرسل **كوداً** — يُعدّل النص.

### S1-08 — مراجعة الأدمن (API فقط)

لا توجد شاشات، لكن الـ endpoints ضرورية لاختبار باقي المسار ولإعطاء شارة التوثيق.

- قائمة الحسابات `pending` مع فلترة بالنوع
- عرض بيانات الحساب ومرفقاته
- اعتماد → `verified_at` يُملأ وتظهر شارة «موثّق»
- رفض → إلزامي كتابة سبب، ويُخزّن ويُرسل لصاحب الحساب
- إيقاف/إعادة تفعيل الحساب
- كل قرار يُسجّل في `account_reviews` باسم الأدمن وتاريخه

**الفرق عن الوثيقة القديمة:** الاعتماد لم يعد بوابة دخول — الحساب يعمل قبله وبعده (بشرط تحقق البريد)، والفرق الوحيد هو ظهور شارة التوثيق.

## 5. قواعد موحّدة

### شكل الاستجابة

```json
// نجاح
{ "success": true, "data": { }, "message": "..." }

// خطأ تحقق (422)
{ "success": false, "message": "...", "errors": { "email": ["..."] } }
```

اكتبه مرة واحدة في `ApiResponse` trait واستخدمه في كل Controller.

### رقم الهاتف

- `+970` ثابت، غير قابل للتعديل أو الحذف من الواجهة
- 9 أرقام تبدأ بـ `59` أو `56`
- يُخزّن دائماً `+970XXXXXXXXX`
- **التحقق على السيرفر إجباري** — regex: `/^\+970(59|56)\d{7}$/`

### 5.1 تدفق تحقق البريد عند التسجيل

1. endpoint التسجيل يتحقق من المدخلات وينشئ سجل `users` (وسجل جدول الدور إن وجد) بـ `email_verified_at = NULL`.
2. **لا يُصدر توكن.** الاستجابة تُرجع فقط `{ success: true, data: { email: "j***@example.com" }, message: "..." }`.
3. يُولَّد كود من 6 أرقام بـ `purpose = register` ويُرسل للبريد.
4. الفرونت يعرض شاشة الكود (12.png).
5. `POST /api/auth/verify-email { email, code, purpose: "register" }`:
   - كود خاطئ أو منتهي → 422، بدون أي أثر على رصيد إعادة الإرسال.
   - كود صحيح → تعبئة `email_verified_at = now()`، إلغاء الكود، إصدار توكن Sanctum وإرجاعه — المستخدم دخل الموقع.
6. `POST /api/auth/resend-code { email, purpose: "register" }` — يخضع لقواعد §5.3.

### 5.2 كلمة المرور

**القاعدة النهائية (محسومة):** 8 أحرف على الأقل + حرف كبير واحد + رقم واحد + رمز خاص واحد. تُطبَّق في `PasswordRule` واحدة يستخدمها كل FormRequest تسجيل، وأيضاً خطوة «كلمة مرور جديدة» في استعادة كلمة المرور.

**حقل تأكيد كلمة المرور إلزامي في نماذج التسجيل الأربعة** (عميل، حرفي، مؤسسة، مقاول) وفي خطوة «كلمة مرور جديدة». استخدموا قاعدة `confirmed` من لارافيل على حقل `password` في كل FormRequest يحتوي كلمة مرور.

### 5.3 قواعد الكود الموحّدة (تسجيل واستعادة معاً)

| القاعدة | القيمة |
|---|---|
| طول الكود | 6 أرقام |
| صلاحية الكود | **3 دقائق** |
| تهدئة إعادة الإرسال | 45 ثانية |
| حد إعادة الإرسال | 3 مرات في الساعة، لكل بريد + `purpose` |
| التخزين | hashed، أبداً نص صريح |
| إعادة الاستخدام | استخدام واحد فقط — يُلغى عند التحقق الناجح **أو** عند إصدار كود جديد |
| محاولة كود خاطئ | **لا تُحتسب** من رصيد إعادة الإرسال — فقط عمليات الإرسال الفعلية تُحتسب |

### 5.4 الدخول والحسابات غير المتحقّقة

يفحص `login` قيمة `email_verified_at` قبل أي شيء آخر:

- `NULL` → لا تسجيل دخول. يُصدر كود جديد بـ `purpose=register` وتُرجع استجابة 403 توجّه الفرونت لشاشة الكود، وليس رسالة «بيانات دخول خاطئة» العامة.
- قيمة موجودة → المتابعة بفحوصات بيانات الدخول والقفل المذكورة في S1-02.

### الرفع

- الصيغ: JPG / PNG / PDF
- الحد الأقصى: **10 ميجا** (حسب التصاميم)
- التحقق من **نوع الملف الفعلي (MIME)** لا من الامتداد
- التخزين: `storage/app/public` مع `php artisan storage:link`
- ضع الحدود في `config/upload.php` لا مبعثرة في الكود

### المصادقة

Laravel Sanctum. `remember` يطيل عمر التوكن. الاستجابة تحمل `role` و `status` وحالة التوثيق.

### Middleware

| الاسم | الوظيفة |
|---|---|
| `role:{roles}` | يحصر المسار بأدوار محددة (مسارات الأدمن) |
| `active.account` | يمنع الحساب الموقوف من كل شيء |
| `verified.email` | يمنع الحسابات بـ `email_verified_at = NULL` من المسارات المحمية (طبقة حماية إضافية، راجع §6.5 بملف SKILL) |

> `approved.account` **غير مطلوب بهذا السبرنت** — الاعتماد لم يعد بوابة. أعدّه لاحقاً عند بناء الطلبات والعروض إذا قرر الفريق حصرها بالموثّقين.

## 6. قاعدة البيانات

### الأساس

```

activity_types    id, name, is_active, timestamps        -- طبيعة نشاط المؤسسة
```

جدول `areas` يبقى باسمه التقني كما هو — تغيّرت فقط تسميته في الواجهة (راجع أعلاه).

**العلاقات:** `Governorate` تملك عدة `Area` (`hasMany`) وعدة `User` (`hasMany`)؛
`Area` تتبع لـ `Governorate` واحدة (`belongsTo`).

**Seeders:** محافظات قطاع غزة الخمس (شمال غزة، غزة، دير البلح، خان يونس، رفح) وتحت كل
محافظة مناطقها · الحرف الثلاث للـ MVP (سباك، كهربائي، فني تكييف) · قائمة أنواع النشاط.

## 8. خطة التنفيذ

### الأسبوع 1 — الأساس
1. Migrations: `governorates`, `areas`, `services`, `activity_types`, `users`
2. Seeders: محافظات ومناطق غزة + الحرف + أنواع النشاط
3. endpoints البيانات المرجعية الأربعة
4. Sanctum + `ApiResponse` trait + `PasswordRule` + `PhoneRule`
5. **الهدف:** الفرونت يعبّي قوائم المحافظات وعناوين السكن والحرف

### الأسبوع 2 — العميل والدخول والتحقق
6. `register/customer` + FormRequest كامل (بدون إصدار توكن)
7. جدول `otp_codes` + `verify-email` + `resend-code` (تسجيل واستعادة معاً)
8. `login` مع فحص `email_verified_at` والقفل والتحويل حسب الدور + `logout` + `me`
9. مسار نسيان كلمة المرور كامل (`forgot-password` + `reset-password`)
10. **الهدف:** عميل يسجّل، يتحقق من بريده، يدخل، ويستعيد كلمة مروره

### الأسبوع 3 — الأدوار المهنية
11. Migrations: `craftsmen`, `institutions`, `contractors`, `attachments`
12. `POST /api/uploads` مع تحقق MIME والحجم
13. endpoints التسجيل الثلاثة (بدون إصدار توكن، نفس تدفق التحقق)
14. `GET /api/profile` و `PUT /api/profile`
15. **الهدف:** الأدوار الأربعة تسجّل وتتحقق وتدخل

### الأسبوع 4 — الأدمن والإغلاق
16. `account_reviews` + endpoints الأدمن الستة
17. إشعار صاحب الحساب بالقرار
18. Feature tests لكل مسار (تشمل حالات الكود الخاطئ/المنتهي وحدود إعادة الإرسال)
19. Postman collection موثّقة ومسلّمة للفرونت
20. **الهدف:** السبرنت مغلق وقابل للعرض
